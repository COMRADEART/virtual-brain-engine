# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout

This is a multi-process project, not just a Vite app. The cooperating pieces:

- `src/` — Vite + React + Three.js frontend (the brain visualizer + Brain OS UI).
- `server/` — Express + TypeScript backend on `127.0.0.1:8787`. SQLite (via `better-sqlite3` + `sqlite-vec`), Ollama connector, 7-step reasoning pipeline, WS broadcast. Now also hosts the memory ML layer, learned ranker, TS agentic layer, digital twin, and the Phase 2 organism/swarm/evolution/imagination subsystems.
- `shared/` — pure-TypeScript type definitions imported by both frontend and server (no runtime deps). `pipeline.ts`, `memory.ts`, `connector.ts`, plus the Phase 2 contracts `twin.ts`, `swarm.ts`, `evolution.ts`, `imagination.ts`, `organism.ts`, `phase2.ts`.
- `src-tauri/` — Tauri 2 desktop shell (Rust). Wraps the Vite build and adds local file/system-monitor commands. Optional; the web app runs without it. Consumes the root `crates/` as path dependencies (see below).
- `crates/` — 7 Rust crates (`brain-autonomous-runtime`, `brain-context-engine`, `brain-knowledge-graph`, `brain-personality-engine`, `brain-semantic-memory`, `brain-temporal-engine`, `brain-workflow-engine`) implementing **Phase 2** per `docs/PHASE2_ARCHITECTURE.md`. **There is no root `Cargo.toml`** — these are not a standalone workspace; they are built only via the root `src-tauri/Cargo.toml` path deps. The Tauri-managed `Phase2System` lives in `src-tauri/src/phase2.rs`.
- `computer-brain/` — a **separate, self-contained Cargo workspace** (28 crates + its own `apps/desktop-pet/src-tauri` Tauri app) implementing a more ambitious local-first cognitive nervous system. Architecture is documented in `computer-brain/docs/ARCHITECTURE.md`; build steps in `computer-brain/docs/BUILD.md`. It does not share code with the root project.
- `worker/` — Python sidecar for **Phase 3 perception** on `127.0.0.1:8789`: `POST /transcribe` (`faster-whisper`) and `POST /caption` (BLIP via `transformers`). Heavy ML deps are gated to `requirements-ml.txt` and imported lazily; the MVP server keeps booting (and `/api/perceive/status` reports `down`) when the worker isn't running. Routes are mounted on the Node side at `/api/perceive/*`.

> **Two Rust workspaces, overlapping crate names.** The root Phase 2 crates under `crates/` were renamed to `brain-*-engine` / `brain-*-memory` / `brain-autonomous-runtime` to avoid collisions with the same-named crates under `computer-brain/crates/`. Always check which workspace you're in before editing. Root crates serve the root Tauri shell; `computer-brain/` crates serve the `computer-brain/` desktop-pet app.

The forward-looking design specs `PERSONAL_MEMORY_BRAIN_SPEC.md` and `DIGITAL_TWIN_SPEC.md` describe intended direction, not the current contract — read them for *why*, read the code for *what is*.

The frontend and server communicate over HTTP (`/api/...`) and a single WebSocket at `/ws/brain`. Pipeline events also stream over SSE on `POST /api/ask`. Both the SSE stream and the WS broadcast carry the same `PipelineEvent` shape (defined in `shared/pipeline.ts`) so that any open tab sees activity even if it didn't initiate the request.

### Per-phase verification ritual (Plan Civil — the "verification floor")

A change is **not done when `npm run gate` is green** — the gate boots the server but no LLM, and history shows runtime-fatal bugs shipping green this way. Every cognition/perception/render change must clear a runtime check matched to what it touched:

1. **`npm run gate`** — typecheck + all selfchecks + server-smoke. Must include the change's own new hermetic selfcheck (temp DB via `BRAIN_DB_PATH`, unreachable worker via `PERCEPTION_WORKER_URL=http://127.0.0.1:1`).
2. **Pipeline / cognition changes** → `GATE_ASK_SMOKE=1 npm run gate` (or `npm run ask:smoke`): a LIVE `POST /api/ask` that asserts the 7-step pipeline completes end-to-end and routed regions/citations are real. Skips cleanly when no Ollama, so it's an **opt-in** gate tail, not a default-blocking step. Its companion `npm run ws:smoke` (`scripts/smoke-ws.mjs`) opens a `/ws/brain` client during a live ask and asserts pipeline frames **+ region flashes actually reach the bus** — the frontend↔backend↔WS broadcast path the hermetic gate can't see (a broken `broadcast()` ships green otherwise). It rides the same `GATE_ASK_SMOKE` tail and the nightly-live CI lane. **New hot-path behavior earns a runtime check here, not just a hermetic selfcheck #N** — the green gate boots no LLM and no browser.
3. **Render changes** → `VERIFY_GPU=1 npm run verify:canvas` (spiking/GPU path) and plain `npm run verify:canvas` (SwiftShader fallback); `npm run test:actions` for lateralization.
4. **UI surfaces** → manual `npm run dev:all` smoke of the touched panel.

Keep new public surface behind existing routers/seams — do not add pipeline call sites or panels that only the gate exercises.

### CI

`.github/workflows/gate.yml` runs the full `npm run gate` on every push/PR (ubuntu, Node 22, no LLM — every selfcheck is hermetic). `.github/workflows/nightly-live.yml` is the runtime tail the default gate lacks: nightly (03:00 UTC, or manual `workflow_dispatch`) it installs Ollama, pulls `llama3.2:1b` + `nomic-embed-text`, and runs `GATE_ASK_SMOKE=1 npm run gate` so the LIVE `/api/ask`, agent-loop, and egress-gate smokes execute against a real model. ### verify:canvas

`scripts/verify-canvas.mjs` is the project's end-to-end check. It launches headless Chrome/Edge via the Chrome DevTools Protocol (no Puppeteer dependency), navigates to `VERIFY_URL` (default `http://127.0.0.1:5173/`), samples a 96×60 region of the `<canvas>`, and asserts that ≥90 pixels have luma >24 — i.e. the Three.js scene is actually drawing, not just mounting. It also captures `Runtime.exceptionThrown` and console errors, writes a screenshot to `artifacts/virtual-brain-engine.png`, and exits non-zero on a blank canvas or any thrown exception. Use this to confirm rendering works after non-trivial changes to `BrainScene`, `NeuralGraph`, `BrainShell`, or the simulation/graph generator. Override the target with `VERIFY_URL=...`.

## Architecture

### The two layers the brain visualises

The repo carries **two parallel region taxonomies** — keep them straight when editing:

1. **Anatomical regions** — ~30 string-literal IDs in `src/engine/types.ts` (`BrainRegionId`) and `src/data/regionDefinitions.ts`. These drive what the user sees in the 3D scene. The renderer in `src/components/NeuralGraph.tsx` indexes everything by these IDs.
2. **Logical regions** — 8 high-level cortices defined in `shared/pipeline.ts` (`LogicalRegionId`: `memory-core`, `reasoning-cortex`, `project-cortex`, `file-memory`, `model-hub`, `response-center`, `error-detection-center`, `learning-feedback-center`). The server emits these in `PipelineEvent.logicalRegions`. The frontend maps each logical region onto a set of anatomical IDs via `src/engine/logicalRegions.ts` (`LOGICAL_REGION_MAP`) and flashes them in the scene.

Adding a new logical region means updating both `shared/pipeline.ts` (`LogicalRegionId` union + `LOGICAL_REGION_IDS` list) **and** `src/engine/logicalRegions.ts` (`LOGICAL_REGION_MAP` + labels). Adding a new anatomical region means updating `src/engine/types.ts` (`BrainRegionId`), `src/data/regionDefinitions.ts`, and the `REGION_CONNECTIONS` adjacency list in `src/engine/brainRegions.ts`.

### Rendering vs. React boundary (the core design choice)

The simulation state — `regionIntensity`, `pathwayIntensity`, and the `pulses` array on `SignalSimulation` — is **deliberately held outside React** as mutable Float32Arrays / a mutable array. React owns *config* (selected action, speed, density, visibility, shell opacity, camera preset); the render loop in `BrainScene` calls `simulation.step(delta, elapsed)` and then `graphRenderer.update(...)` every frame, mutating instance matrices and color buffers directly. **Do not lift per-frame simulation state into React state** — it would trigger re-renders at 60 Hz and defeat the whole architecture. When you need React to react to a config change, route it through one of the `simulation.setX(...)` methods (already wired in `BrainScene` effects).

### Frontend data flow

1. `App.tsx` holds all user-facing config in `useState` and passes it to `BrainScene`, `RegionControls`, `InfoPanel`, plus the auxiliary overlays (`PipelineOverlay`, `LogicalRegionIndicator`). The Phase 2 panels and brain-os shells are enumerated in point 6 below.
2. `BrainScene` (`src/components/BrainScene.tsx`) is the single Three.js host. One `useEffect` builds the scene/renderer/camera/controls/shell on mount. A separate effect, keyed on `neuronDensity`, rebuilds the `NeuralGraph` and swaps in a fresh `NeuralGraphRenderer` + `SignalSimulation`. Other props feed `simulation.setAction / setSpeed / setRunning`, `setBrainShellOpacity`, and `graphRenderer.applyRegionVisibility` through small effects — those don't tear down the scene.
3. The render loop reads refs (`visibilityRef`, `selectedRegionRef`) rather than closing over props so the single long-lived `renderFrame` keeps seeing the latest values without re-subscribing.
4. Region clicks come from raycasting against the invisible region volume meshes exposed as `graphRenderer.regionMeshes`; the hit's `userData.regionId` is sent back up via `onRegionSelect`.
5. `BrainScene` also subscribes to `brainBus` (the WS singleton, see below). When a `pipeline` message arrives, it expands `event.logicalRegions` through `LOGICAL_REGION_MAP` and flashes the resulting anatomical IDs.
6. **Brain OS layout modes.** `src/engine/useLayoutMode.ts` owns a `LayoutMode` (normal / `CompactLayout` / `FocusMode`); `App.tsx` reads it (`App.tsx:53`) and renders the matching shell from `src/components/brain-os/` (`CompactLayout`, `FocusMode`, `CommandPalette`). The `CommandPalette` (toggled via `useCommandPalette`) is the keyboard entry point for switching modes and opening the Phase 2 panels (`DigitalTwinPanel`, `SwarmPanel`, `EvolutionPanel`, `OrganismPanel`, `ImaginationPanel`, `Phase2CortexPanel`, `UnifiedPanel`). Auto-quality (`useAutoQuality`/`adaptiveQuality`/`performancePresets`) scales render cost to sustain 60 FPS; route quality changes through those, not ad-hoc renderer tweaks.

### Engine layer (`src/engine/`)

- `types.ts` — all shared types. `BrainRegionId` and `BrainActionId` are string-literal unions.
- `brainRegions.ts` — derives `REGION_ORDER`, `REGION_INDEX`, `REGION_BY_ID`, `ACTION_BY_ID` lookup tables from the data file, and defines `REGION_CONNECTIONS` (inter-region edge counts) used by the graph generator.
- `logicalRegions.ts` — maps the 8 logical regions to anatomical IDs. Pure data file; no runtime dependencies.
- `neuralGraphGenerator.ts` — deterministic graph builder seeded by `density` (seed = `round(density*1000)+19` in `BrainScene`). Produces `NeuralGraph` with `nodes`, `pathways`, `regionRanges`, `regionOrder`, and a flat `nodePositions` Float32Array. Uses an O(n) sliding-window heuristic for intra-region locality rather than a true nearest-neighbor pass — keep that property if you change it.
- `signalSimulation.ts` — `SignalSimulation` owns the mutable intensity buffers and pulse list. `step()` decays intensities, spawns weighted pulses biased toward the active action's regions (`rebuildEligiblePathways` precomputes the eligible set on action change), advances each pulse along its pathway, and reflects pulse progress back into region/pathway intensity. `MAX_PULSES = 260` caps the active pool. Random number generation is seeded (mulberry32) so replays are deterministic.
- `apiClient.ts` — typed wrapper around the local `/api` surface. Default base URL `http://127.0.0.1:8787`, overridable with `VITE_BRAIN_API_URL`. Includes `ask()` which is an `async *` generator that parses the SSE stream from `POST /api/ask` and yields each `PipelineEvent`.
- `brainBus.ts` — singleton WebSocket client for `/ws/brain`. Backoff is 1s → 30s (doubling) with quiet logging — the first failure is logged, subsequent reminders are throttled to ~60s, and on a successful reconnect the backoff resets. The bus does **not** require the server to be up; it just keeps retrying. A `window.__brainBus.emit(...)` helper is exposed in dev for testing pipeline events without a backend.
- `audioBus.ts` — the ambient audio bus (`createAmbientBus`) consumed by `BrainScene`. (The former browser→Ollama "AI Companion path" — `ollamaClient`/`aiCompanion`/`speechInput`/`speechOutput` — has been removed; the companion surface is now the desktop pet, which talks to the server via `/api/agent`.)

### Renderer details (`src/components/NeuralGraph.tsx`)

`NeuralGraphRenderer` packs all neurons into a single `InstancedMesh`, all pathways into one `LineSegments` with a per-vertex color `BufferGeometry`, and all pulses into a second `InstancedMesh`. Hiding a region is done by writing a zero-scale matrix for its neurons, not by toggling `visible` on individual meshes. Region volumes (the clickable hit-test shells) live in `regionMeshes` and are the only objects the raycaster intersects.

**The million-neuron field (`src/components/NeuronField.ts`).** The `NeuralGraphRenderer` above stays BOUNDED (a few thousand neurons) because the parts that scale badly — synaptic PATHWAYS and the per-frame color/matrix rewrites — are tied to its neuron count. To render ~1,000,000 neurons, `NeuronField` renders the OTHER neurons as a single `THREE.Points` cloud with a custom shader: per-neuron data (position / size / region index / phase) is built ONCE into typed arrays (no per-node JS objects), and color + activity are driven by SMALL per-REGION uniform arrays (≈28 floats) the vertex shader looks up by each point's region index. So per-frame CPU cost is **O(regions), not O(neurons)** — the GPU draws a million 1-vertex points happily. It has no pathways, pulses, or raycast targets (those remain the interactive mesh's job) and reads the SAME `simulation.regionIntensity`/`regionFlashIntensity` buffers, so it lights up in lock-step. `BrainScene` builds it in a standalone effect keyed on `uiPrefs.neuronFieldCount` (Settings → Scene → "Neurons"; default **1,000,000**) and drives it in `renderFrame`; `BrainScene.effectiveFieldCount` caps the count down to 50k on a software/SwiftShader renderer (so `verify:canvas` never blanks) and allows the full count on GPU-capable hardware. The StatusBar neuron readout reports the COMBINED total (interactive graph + field).

### Server (`server/src/`)

- `index.ts` — Express bootstrap. Opens the SQLite DB, ensures a default connector exists, kicks off connector probing (every 30s), wires the routers under `/api`, then attaches the WS hub via `attachBrainBus(server)`.
- `config.ts` — env-driven config (`PORT`, `HOST`, `DEFAULT_SCAN_ROOT`, `OLLAMA_BASE_URL`, `OLLAMA_CHAT_MODEL`, `OLLAMA_EMBED_MODEL`, `EMBEDDING_DIM`, `MAX_FILES_PER_SCAN`, `MAX_FILE_BYTES`, `ALLOWED_ORIGIN`). Defaults are picked to work zero-config on the developer machine. **`CONFIG` is mutated in place by the runtime-settings layer** (see below) — every read site does `CONFIG.x` at call time and **nothing destructures it at import**, so a live override is picked up everywhere; keep that property if you add config reads.
- **Runtime settings — "edit the brain's own knobs from the UI"** (`settings/runtimeSettings.ts` + `routes/settings.ts` + `shared/settings.ts` + `SettingsPanel`'s `BrainSettingsSection`). A curated, runtime-safe subset of `ServerConfig` (privacy/network, speed, retrieval, reasoning, actions, models, memory, cognition) is exposed as editable settings. `SETTINGS_CATALOG` maps each `key` 1:1 onto a `CONFIG` property + its env var; `applyPersistedSettings()` (called early in `index.ts` `main()`) overlays saved overrides onto live `CONFIG`; `GET /api/settings` returns the catalog + current values, `POST /api/settings` validates a `{patch}` (clamps numbers, checks enums, rejects unknown keys) → mutates `CONFIG` → persists the **diff-from-baseline** as one `brain_metadata` JSON row (no schema/migration), `POST /api/settings/reset` restores the env baseline. **Honesty:** knobs read once at boot to wire an interval/schedule (`sleepCycle`, `workspaceEnabled`) are flagged `requiresRestart`; everything else is live. **Security:** secrets/keys are NEVER in the catalog (they stay in `.env`); `localOnly`/`allowShell`/`dedupAutoMerge` are `danger`-flagged. Validated by `npm run settings:selfcheck` (hermetic, baseline-agnostic).
- **Read any file into the brain** (`settings/fileExtract.ts` + `settings/fileIngest.ts` + `POST /api/ingest/file` + `SettingsPanel`'s `FileIngestSection`). The "upload a file, the brain reads it" surface. `fileExtract.ts` is PURE + dependency-free: text/code → UTF-8, HTML/SVG → `htmlToText`, **PDF → best-effort** (Node `zlib` inflates FlateDecode streams, then pulls text from content-stream string operators), **Office docx/pptx/xlsx → a minimal central-directory ZIP reader** (zlib `inflateRaw`) + XML strip, opaque binary → `strings`-style printable salvage (or nothing, reported honestly). `fileIngest.ts`'s `ingestUploadedFile` routes **images → `deps.caption` (BLIP via the perception worker)** and everything else → `extractTextFromFile` → `chunkText` → `ingestExplicitEmbedded("file", …)` (the new `"file"` ingest source; an upload IS its own consent, so no ambient-consent gate). `deps` (caption + embed) are INJECTED so it's hermetically testable. The route installs its OWN 40mb `json()` (file base64 exceeds the global 1mb cap; `index.ts` lets `/api/ingest/file` bypass the global parser, exactly like `/api/perceive/*`). Validated by `npm run fileingest:selfcheck` (hermetic — hand-built PDF + stored-zip docx, NO worker/network).
- `db/sqlite.ts` — opens `data/brain.sqlite` (WAL mode, FKs on), loads the `sqlite-vec` extension if available, and applies `db/schema.sql` on every boot (the schema is fully idempotent). The vec extension is **optional** — if `sqlite-vec` fails to load, the server keeps running and `vectorSearch` becomes a no-op; the frontend's `/api/health` reflects that as `vector: "unavailable"`.
- `db/schema.sql` — the authoritative, idempotent schema, now grown to ~50 tables across all the subsystems. The MVP core is `memory_points`, `memory_relations`, `conversations`, `messages`, `pipeline_runs`, `connectors`, `scan_roots`, `files`; the rest back the ML/learning layer (`ranker_state`, `answer_feedback`, `rank_training_log`, `ranker_loss_history`, the `memory_access_*`/`memory_clusters`/`memory_*_patterns` tables), the twin/organism/imagination/evolution subsystems, actions/ingest (`action_log`, `dynamic_actions`, `ingest_consent`, `ingest_log`), vision (`visual_memory`, `visual_regions`, `visual_workflow_states`), and `brain_metadata` (KV used by the adaptive layer + BrainState). Migrations are tracked in `schema_migrations`. The `memory_vec` virtual table is created at load time inside `loadVectorExtension` (the only schema piece *not* in `schema.sql`, because its existence depends on the extension loading). Read `schema.sql` for the current truth — don't trust this summary to be exhaustive.
- `db/repositories/` — one file per aggregate (`memory.ts`, `conversations.ts`, `connectors.ts`, `scan.ts`). Repositories return the typed shapes from `shared/memory.ts` and `shared/connector.ts`.
- `connectors/` — pluggable LLM connectors. `Connector.ts` defines the interface (`send`, `stream`, optional `embed`, `test`). Concrete impls: `OllamaConnector` (default) and the unified `OpenAICompatibleConnector` (local runtimes + curated remote providers — see "Purely-local guarantees" below), plus `stubs.ts`. `registry.ts` resolves the configured default and runs the local-runtime auto-discovery; `discovery.ts` probes the known ports; `ollamaModels.ts` lists/pulls installed Ollama models for the Model Hub.
- `reasoning/pipeline.ts` — the **7-step pipeline**: `input` → `memory` (embed + vector search + recency/importance boost) → `reasoning` (JSON plan) → `project` (project-name rerank) → `error` (contradictions/missing/confidence JSON) → `response` (streamed answer in three sections: `Known memory:` / `Inferred reasoning:` / `Uncertain:`) → `learning` (persist Q+A as a new `MemoryPoint`, link to cited memories). Each step calls `emitAll(...)` which **both** sends the event over SSE (to the originating request) and broadcasts it on the WS hub (to every subscribed tab). Markers in the answer have the form `[m:<id>]` and are validated against the set of memories actually retrieved — unknown IDs are stripped and a note is appended to the Uncertain section.
- `reasoning/prompts.ts` — system prompts for reasoning/project/error/response. The response prompt is parameterised by whether memory was found.
- `routes/` — Express routers, all mounted under `/api` in `index.ts`. The MVP core is `health`, `memory`, `scan`, `connectors`, `ask` (SSE), `conversations`. Every Phase 2 / FRIDAY / cognitive subsystem mounts its own router alongside these (`agent`, `feedback`, `learning`, `actions`, `skills`, `repo`, `ingest`, `web`, `github`, `models`, `brain`, `twin`, `swarm`, `imagination`, `evolution`, `organism`, `vision`, `perceive`, `phase2`, `civilization`) — most are documented in their own section below, not re-listed here. (`phase2` is the exception: `routes/phase2.ts` is the **browser fallback** for the Phase 2 cognitive surface — the Tauri build serves these from the `brain-*` Rust crates via `src-tauri/src/phase2.rs`, and `apiClient` routes `phase2*` calls to Tauri when in-app; the Node router returns real data where it has a SQLite backing and shaped-but-empty values for the desktop-only crates.) `index.ts` is the authoritative mount order.
- `scanner/` — `walker` (recursive directory walk with ignore rules and budget caps), `chunker` (file → text chunks), `indexer` (chunk → `MemoryPoint` + embedding). The scan budget is `CONFIG.maxFilesPerScan` × `CONFIG.maxFileBytes` to keep an accidentally-pointed-at-`C:\` scan from spiralling.
- `ws/brainBus.ts` — WS hub at `/ws/brain`. Exports `broadcast(message)` which the pipeline and scanner call to fan out `BrainBusMessage`s.

### Server Phase 2 subsystems (memory ML, agents, twin, organism)

These bolt onto the same Express process; they don't replace the 7-step pipeline, they run alongside it.

- `memory/` — the **memory ML layer**: `importanceScorer`, `memoryStrength`, `memoryLifecycle`, `consolidationEngine`, `noveltyDetector`, `predictivePrefetch`, `semanticCluster`, `accessPatternTracker`, `thresholdController`. The integration seam is narrow and deliberate: the pipeline only imports `onConversationMessage` / `processNewMemory` from `consolidationEngine` and `updateMemoryImportance` from `memoryLifecycle` (see `reasoning/pipeline.ts`). `index.ts` calls `scheduleDecayTick()` (from `consolidationEngine`) at boot to run periodic decay/consolidation in the background. Treat the rest of `memory/` as a library these two seams pull from — don't add new pipeline call sites without a reason.
- **Data safety + transparency** — four small, cooperating guarantees: **(1) backups** — `backup/index.ts` snapshots `brain.sqlite` with `VACUUM INTO` on boot + daily (`BACKUP_ENABLED`/`BACKUP_INTERVAL_HOURS`/`BACKUP_KEEP`), retention-pruned into `data/backups/`; manual trigger `POST /api/memory/backup`, list `GET /api/memory/backups`, plain-text corpus export `GET /api/memory/export`. **(2) reversible dedup** — `mergePair` tombstones the loser row + relations into `memory_tombstones` before deleting; `GET /api/memory/tombstones` + `POST /api/memory/tombstones/:id/restore` undo a merge (embedding excepted — re-derivable). **(3) the Memory Inspector** — the bus-gated `MemoryInspectorPanel` (browse/search/forget memories with provenance, restore merged-away ones, export) is the "what do you know about me / forget it" surface. **(4) injection fencing** — `reasoning/untrusted.ts` marks `ingest:web`/`ingest:github` memories as untrusted and fences their snippets in every LLM prompt (pipeline + agent loop) as quoted DATA with spoof-proof markers; the standing rule lives in `COGNITIVE_PRINCIPLES`/`ERROR_SYSTEM`. Validated by `backup:selfcheck`, `dedup:selfcheck`, and `injection:selfcheck`. Related flywheel: every 👍 on an answer captures the run's (prompt, answer) into `sft_pairs` (`/api/learning/sft/{status,export}`, JSONL) so a future LoRA pass can do REAL instruction SFT; a 👎 retracts the pair.
- `reasoning/ranker.ts` + `rankerModel.ts` + `db/repositories/ranker.ts` — a small learned ranker that re-scores memory retrieval. `rankerModel.ts` holds the model/weights, `ranker.ts` the scoring entrypoint, the repository its persisted training signal. Validated by `npm run ranker:selfcheck`.
- `agents/` — a TS agentic layer (`Agent.ts` base, `runtime.ts`, `observerAgent`, `summaryAgent`, `schedulerAgent`, `systemSensorAgent`, `idleAgent`, `brainCore.ts`). `index.ts` calls `startBrainCore()` at boot; the runtime isolates agent init so a misbehaving agent never blocks server startup. The `IdleAgent` (blueprint Phase 1) emits an `idle-thought` bus event when the system has been quiet for ≥90s AND ≥5min has elapsed since its last emission; it samples a recent memory weighted by `importance × saliency` (geometric mean), where saliency is built from the organism singleton's `getActiveGoalTitles()` + `getHealthScore()`. The agent layer is the Node-side analogue of the `computer-brain/` Rust agent system — they are not the same code.
- `twin/` — the digital twin: `collectors` + `snapshotEngine` capture system state, `cpuMath`/`predictiveModel` forecast, `anomalyDetector` flags drift, `simulationEngine` runs what-ifs, `repository` persists. Surfaced at `/api/twin`. Validated by `npm run twin:selfcheck`.
- `core/` — `eventBus` plus the four Phase 2 organism subsystems `evolution`, `imagination`, `organism`, `swarm`, and a `safety` gate. Each has a matching router mounted under `/api` in `index.ts` (`/api/twin`, `/api/swarm`, `/api/imagination`, `/api/evolution`, `/api/organism`) and a `shared/` type contract. These are experimental — keep new public surface behind these routers, not inside the pipeline. **Phase 3 hierarchy:** `core/abstractionLevels.ts` is the deterministic 6-level (0 sensory → 5 philosophical) classifier used by `imagination.upsertAbstraction()` to fill the new `cognitive_abstractions.level` column. Re-classify can only promote, never demote (`Math.max(existing.level, classified)`); the 0002 migration backfills pre-existing rows to 0.
- `attention/` — `saliency.ts` is the unified [0,1] retrieval-time saliency scorer (blueprint Phase 1 highest-leverage gap). Pure, deterministic, zero DB deps — the caller (today `reasoning/pipeline.ts`'s `buildSaliencyContext`) assembles the `SaliencyContext` from the organism singleton. Fuses novelty (storage-time if available, else query↔memory dissimilarity), goal-relevance (jaccard on active goal titles), emotion (importance pass-through), and survival (low-health gate × survival-term scan) into one blended score. `rankHits(hits, saliencyCtx?)` accepts it optionally — omitting the context preserves the legacy ranker behavior. Validated by `npm run attention:selfcheck`.
- `perception/` — Phase 3 perception layer (`workerClient.ts` + `index.ts` router). Forwards `POST /api/perceive/transcribe` and `POST /api/perceive/caption` to the Python sidecar at `127.0.0.1:8789` (override via `PERCEPTION_WORKER_URL`). 200ms timeout on the probe (`/api/perceive/status` and `/api/health.perception`), 60s on real calls. Failures route through `surfaceError("perception:...")` so the `/api/health.diagnostics` counters see them; the probe path uses `quiet: true` so a worker that's intentionally down does not bump the counter on every health hit. The router installs its own `express.json({ limit: "20mb" })` since the global cap is 1mb. Validated by `npm run perception:selfcheck` (hermetic — no worker required).
- **Learning Lab** (`learning/` + `routes/feedback.ts` + `routes/learning.ts` + the `LearningLabPanel`) — surfaces and feeds the brain's OWN learning ("train the brain like an LLM"). Three layers: **(A) explicit feedback** — `POST /api/feedback` ({runId, rating ±1}) retrains the learned ranker against the user's verdict (`trainFromFeedback`, no warm-up double-count) and nudges cited memories' importance; the pipeline persists a per-run training snapshot (`rank_training_log`) so feedback can retrain against the SAME feature vectors that produced the ranking. **(B) visibility** — `GET /api/learning/status` exposes ranker warm-up/α, labelled weights (`FEATURE_LABELS`), training-loss history (`ranker_loss_history`, written at each online update), and 👍/👎 tally; the bus-gated `LearningLabPanel` renders it. **(C) from-scratch LLM** — `learning/llmTrainerClient.ts` ships the brain's own memory corpus (`exportMemoryCorpus`) to the Python worker's `POST /train/start` (a tiny GPT in `worker/train/`, faithful to FareedKhan-dev/train-llm-from-scratch but char-level on the personal corpus — **educational, not a brain upgrade**); `/train/status` polled via `/api/learning/llm/status`. **Boot auto-train + TrainingBar:** the server kicks this training automatically on boot (`AUTO_START_SCRATCH_LLM`, default ON; rate-limited via `brain_metadata` so dev restarts don't retrain — `learning/autoStart.ts`), a Node-side watcher broadcasts `llm-training` bus frames while a run is live, and the frontend `TrainingBar` renders them as a top-center progress bar (smoke: `node scripts/smoke-training-bar.mjs`, needs a live run). The trainer scales its arch by device (cuda → ~15M params, cpu → the tiny toy; `SCRATCH_*` envs), persists checkpoints to `data/scratchllm/` (every 250 steps + at end; float tensors stored fp16 — half the disk, cast back to fp32 on load), and `POST /api/learning/llm/generate` samples from the persisted model on CPU any time — including mid-run. The trainer imports torch lazily and the Node side degrades to `state:"unavailable"` when the worker is down, exactly like perception. Validated by `npm run learning:selfcheck` (hermetic — no worker, no torch). **(D) the brain's OWN model** — `learning/ownModelClient.ts` + `worker/finetune/` + `routes/learning.ts` (`/api/learning/ownmodel/{status,start,serve}`): unlike (C)'s educational from-scratch toy, this produces a model the brain can actually REASON with. A **LoRA continued-pretraining** pass (`worker/finetune/trainer.py`, lazy torch/transformers/peft) over a small open base (default `Qwen/Qwen2.5-0.5B-Instruct`, downloaded from HF on the first run — the one deliberate, user-initiated outbound action) on the brain's own corpus (`exportMemoryCorpus`, shipped Node-side; both this and (C)'s scratch trainer export with `englishOnly` under `TRAIN_ENGLISH_MOSTLY`, default ON — `isMostlyEnglish` in the memory repository drops docs whose non-Latin-script letter ratio exceeds 0.3, so ingested non-English web/GitHub pages can't pull the adapted voice away from English), merged into a standalone HF dir. The training data is **chat-formatted episodes** (each ~1k-char corpus doc wrapped as a user→assistant exchange via the model's chat template), and the default LR is a deliberately **gentle 5e-5** (`OWN_MODEL_LR`): raw-stream CPT or LR 2e-4×250 steps measurably overwrites the instruct base's behavior (no instruction following, no turn-end, corpus regurgitation to the token cap — all three failed recipes verified directly on the merged HF model). When tuning, test the merged HF dir with transformers BEFORE quantize/serve to split model behavior from GGUF/Ollama plumbing. `serveOwnModel()` then runs `ollama create` against that dir — **compressed on import**: when the worker exported an F16 GGUF, the create passes `--quantize` (default `q4_K_M`, the same level Ollama's library models ship as — ~4x smaller at near-identical quality; override with `OWN_MODEL_QUANTIZE` = `q4_K_M`|`q4_K_S`|`q8_0`|`off`; an old Ollama without the flag falls back to the uncompressed import). The Modelfile it writes (`buildModelfile`) is FROM + a `TEMPLATE` block carrying the canonical Qwen2.5 ChatML+`<tool_call>` template — the GGUF embeds Qwen-BASE's template, which has no tools section, so without this every request carrying `tools` (external IDE/agent clients send them) gets a 400 "does not support tools"; the model now ACCEPTS tools but, being CPT-adapted, won't call them well. Deliberately NO `PARAMETER stop` line: on Ollama 0.30.x a model-level stop string makes the runner ignore `num_predict` and decode until the context fills (measured; the identical build minus the stop param respects the cap). Instead `PARAMETER num_predict 1024` is the ramble guard (measured safe; request options override): a CPT base never emits the ChatML turn-end token, so an uncapped client request would otherwise decode to the context limit. It then seeds an Ollama connector via `ensureOwnModelConnector` — **ALWAYS disabled + non-default** (same opt-in pattern as the NVIDIA/Gemini seeds), so a small-corpus voice adaptation never silently becomes the model `/api/ask` uses. **Honest scope:** this adapts the base model's VOICE + domain (continued-pretraining, NOT instruction SFT — a personal brain has thousands of memory chunks but only a handful of real conversation pairs, and SFT on a dozen pairs degrades the base); **RAG stays the knowledge path** and does facts better. No `embeddingModel` on the seeded connector → retrieval keeps using the local nomic embedder, vector index intact. Validated by `npm run ownmodel:selfcheck` (hermetic — worker-down degrade + tiny-corpus guard + serve state-gate + connector seed/idempotency/opt-in + route wiring; NO torch, NO ollama, NO network); the live train→merge→`ollama create`→answer path is the runtime check (GPU: a CUDA torch build; CPU works but slow).
- **FRIDAY command layer — actions + ingest + Model Hub** (the "personal computer brain" surface; the desktop **pet** `src/components/pet/PetWindow.tsx` is its primary UI — a draggable companion whose one command box resolves NL → action, falling through to `/api/ask` for questions). Four cooperating subsystems, all behind their own routers, never inside the 7-step pipeline:
  - `actions/` (+ `routes/actions.ts`, `shared/actions.ts`, `db/repositories/actions.ts`) — a **permissioned** command layer. `registry.ts` is THE allowlist (id → title/risk/`surface`/zod schema). `resolver.ts` asks the connector to map an NL prompt to ONE allowlisted action, then re-validates the model's JSON against the registry (unknown id / bad args / sub-floor confidence → no plan). `executor.ts` is the trust boundary: it re-derives risk + schema from the registry by id (NEVER trusts the submitted plan), enforces a plan-bound single-use **confirm token** for `confirm`-tier actions, runs the handler, and **audits every attempt** (success or refusal) to `action_log`. `surface: "os"` actions (`open-path`, `open-url`) return an `osDirective` the Tauri renderer invokes via `tauri-plugin-opener` (the OS default handler, not a shell — no injection); `src-tauri/src/os_actions.rs` is the executor. **"Do any task on the laptop"** is the confirm-tier `run-command` (arbitrary shell — PowerShell on Windows, `/bin/sh` elsewhere; captured + size-capped output, kill timeout) and `launch-app` (Start-Process / `open`; `app`/`args` are `psSingleQuote`-escaped, run-command is deliberately raw). They are the broadest capability in the brain, so they sit behind `CONFIG.allowShell` (env `ALLOW_SHELL`, **default ON** for this personal computer-brain): when off, `registry.isShellAction`-tagged ids are filtered out of `listActionDefs`/`listActionSpecs` so the resolver/loop/UI can't even propose them, and the executor re-checks the flag. When on they are STILL fully gated — every run needs a confirm token OR a granted session scope and is audited like any other confirm-tier action (the pet's **autonomy** selector drives this: ask / auto = session-scope / read-only). A non-zero exit is returned as a successful tool result (the agent needs to SEE stdout/stderr + exit code); only spawn failure / timeout throws. Validated by `npm run actions:selfcheck` (hermetic) + the live `npm run actions:smoke` tail; `npm run agent:selfcheck` adds a hermetic assertion that `run-command` is confirm-tier and is REFUSED in safe-only mode (no process ever spawned).
  - `ingest/` (+ `routes/ingest.ts`, `shared/ingest.ts`, `db/repositories/ingest.ts`) — **computer-wide memory** capture. `ingestItems()` is the governed choke point: consent gate (opt-in, default OFF) → exclude-path drop → redact EVERY persisted field (`governance.ts`; credentials only, never PII) → content-hash dedup → importance → persist as a `chunk` memory → audit. `ingestExplicit()` is the same governance minus the ambient-consent gate, for deliberate user-initiated paths. The **`web` source = "learn from the internet"**: `webFetch.ts` fetches a URL, extracts readable text (dependency-free `htmlToText`), and chunks it; `fetchAndIngestUrl()` runs the chunks through `ingestExplicit`. **EGRESS is gated by `LOCAL_ONLY`**: the fetcher routes the target through `isLocalUrl()`, so under the default `LOCAL_ONLY=true` only loopback/RFC1918 targets are reachable and internet learning is **blocked with a clear reason — "zero outbound by default" holds**. Internet learning requires `LOCAL_ONLY=false` (the same opt-out as remote LLM connectors; `LocalityBadge` already reads amber then). Reachable as the confirm-tier `learn-url` action (so the pet handles "learn https://…") and directly via `POST /api/ingest/web`. Validated by `npm run ingest:selfcheck` (hermetic — injected fetch, NO network) + the opt-in `npm run web:smoke` runtime tail (boots the real server twice: proves the block under `LOCAL_ONLY=true` and a live fetch under `LOCAL_ONLY=false`; skips when offline).
  - `routes/models.ts` (+ `connectors/ollamaModels.ts`, `reasoning/modelRouting.ts`, `shared/models.ts`, `ModelHubPanel`) — the **Model Hub**: browse/pull installed Ollama chat models (progress over the bus, flashes the `model-hub` cortex) and per-cortex **MoE routing** (`profileForRoute` + `pickModel`, pure; a since-removed assignment falls back to the default model). Assignments are live from boot: `index.ts`'s 60s reconcile cycle union-refreshes the routing availability cache with the local Ollama tag list (`addAvailableModels` — union, not replace, so remote-provider models merged in by `GET /api/models` survive), so a per-profile assignment no longer sits inert until someone opens the Model Hub view. Chat models only — the embedder is fixed (memory_vec dim). Validated by `npm run models:selfcheck` + the opt-in `npm run models:smoke`.
  - `web/` (+ `routes/web.ts`, `shared/web.ts`) — **hybrid local+internet ("FRIDAY goes online")**: the "learn from the internet" + "local & internet side by side" layer. `web/search.ts` is a dependency-free, **pluggable** web search (auto-selects: a local **SearXNG** JSON endpoint → a keyed API **Brave/Tavily/Exa** read from the env → a no-key **DuckDuckGo** HTML fallback), with an injectable fetch. `web/research.ts` orchestrates **search → fetch (`fetchAndIngestUrl`) → govern (redact/dedup) → embed → fuse**: fetched pages are LEARNED (`ingestExplicitEmbedded` embeds the redacted text so they join the vector index) and returned as citeable `VectorSearchHit`s (capped at `MAX_FUSED_HITS=8` for fusion; all chunks still persist). The **7-step pipeline's memory step** calls `webResearch` when `hybridEnabled()` (LOCAL_ONLY=false + `HYBRID_RESEARCH` + mode≠off) AND `shouldAugment()` (the `WEB_SEARCH_MODE` gate: `smart` default only searches on thin/weak local memory or a time-sensitive query; `always`/`ondemand`/`off`) — fully failure-isolated, so a web error never costs the local answer. **EGRESS is the SAME `LOCAL_ONLY`+`isLocalUrl()` gate as web fetch**: under the default `LOCAL_ONLY=true` a local SearXNG still works but every remote search/fetch is blocked before a byte leaves the machine; there is NO remote-host bypass (that exists only for the curated LLM connectors). Surfaced as the confirm-tier `web-search` / `research-web` actions and directly via `POST /api/web/{search,research}`. The action layer also gained **system actions** — `system-info` (safe, read-only metrics) and `list-directory`/`read-file`/`write-file` (confirm-tier, absolute-paths-only, `isExcludedPath`-guarded). Validated by `npm run websearch:selfcheck` (hermetic — injected fetch, NO network) + the opt-in `npm run websearch:smoke` runtime tail (boots the real server twice: block under `LOCAL_ONLY=true`, live search under `LOCAL_ONLY=false`; skips when offline / no provider).
  - `github/` (+ `routes/github.ts`, `shared/github.ts`) — **GitHub project discovery ("learn from popular repos")**: discover the most-starred repos (default >1k via `GITHUB_MIN_STARS`) for a topic and learn their READMEs into citeable memory. `github/discovery.ts` is a dependency-free, injectable-fetch module modeled on `web/search.ts` but **hardened beyond it** — it talks ONLY to `api.github.com` (search `/search/repositories?q=…+stars:>=N&sort=stars`, README via the **base64 JSON envelope** so it's a single 200, no `raw.githubusercontent.com` redirect), and because it only runs with `LOCAL_ONLY=false` it does NOT copy web/search.ts's `localOnly`-gated redirect idiom: `ghFetch` is **always** `redirect:"manual"` + refuses any 3xx, **host-pins** every URL (`new URL().hostname === "api.github.com"`), and validates owner/repo path segments against GitHub's charset so a poisoned search field can't rewrite the host. `github/index.ts`'s `discoverAndLearn` runs `githubSearch → fetchRepoReadme → chunkText → ingestExplicitEmbedded("github", …)` — READMEs go through the SAME governed ingest (redact → dedup → importance → "chunk" provenance `ingest:github`), embedded so they join the vector index; per-repo failure-isolated; a single page (`per_page=GITHUB_MAX_REPOS`, no crawl) bounded further by an `X-RateLimit-Remaining` budget. `GITHUB_TOKEN` (optional, header-only, never persisted) raises GitHub's low unauthenticated rate limit. **EGRESS is the SAME `LOCAL_ONLY`+`isLocalUrl()` gate**: under the default `LOCAL_ONLY=true` `api.github.com` is blocked before a byte leaves the machine (GitHub is deliberately NOT on the curated remote-host allowlist), so discovery needs `LOCAL_ONLY=false`. Redaction also gained the fine-grained `github_pat_` token pattern (`ingest/governance.ts`). Surfaced as the confirm-tier `github-search` / `github-learn` actions and directly via `POST /api/github/{discover,learn}`. It does NOT auto-augment the 7-step pipeline (on-demand only). ### Tauri shell (`src-tauri/`)

Rust app that wraps the Vite build. `tauri.conf.json` sets `devUrl: "http://127.0.0.1:5173"` and `beforeDevCommand: "npm run dev"`, so `npm run tauri:dev` boots Vite for you. `src-tauri/src/lib.rs` registers commands defined in `commands.rs` (system metrics, project watch, git activity, brain activity, memory points, project context). The Rust DB (`database.rs`) is **separate** from the Node server's SQLite DB — it lives under the OS's app-data dir, not in `data/brain.sqlite`. If you're working on data that should be available to both the web app and the desktop shell, route through the Node server, not Tauri commands.

### Worker (`worker/`)

The Python sidecar (`127.0.0.1:8789`). No longer a placeholder — four subsystems route to it, each with lazy ML imports so the worker-down path degrades gracefully: **Phase 3 perception** (`/transcribe`, `/caption` → `/api/perceive/*`), the **from-scratch LLM trainer** (`worker/train/` → `/api/learning/llm/*`), the **brain's own model** LoRA finetune (`worker/finetune/` → `/api/learning/ownmodel/*`), and **AirLLM high-parameter inference** (`worker/airllm_engine/` → `/api/learning/airllm/*`). Heavy ML deps stay gated to `requirements-ml.txt` and are imported lazily, so the MVP server keeps booting with the worker absent (status routes report `down`/`unavailable`). Read `worker/README.md` before adding anything; keep the lazy-import + graceful-degrade contract so the core server never hard-depends on Python being up.

> **AirLLM (`worker/airllm_engine/`) — "use a high-parameter model on a small GPU".** [lyogavin/airllm](https://github.com/lyogavin/airllm) runs 7B…70B (even 405B) models on a 6GB GPU by streaming the transformer **one layer at a time** (resident footprint ~one layer; slow; **inference only**). Two roles: (1) direct generation via `POST /api/learning/airllm/generate` (status `GET /api/learning/airllm/status`); (2) the **distillation teacher** for the `mango` own-model trainer — `POST /api/learning/ownmodel/start { distill:true, teacherModel? }` runs a slow pre-pass where the big teacher rewrites the corpus notes into clean instructional answers, then the small mango student trains on **those** (the teacher is freed *before* the student loads, so they never share the GPU). Distillation is **OFF by default** (`OWN_MODEL_DISTILL`, teacher `AIRLLM_TEACHER_MODEL`=`Qwen/Qwen2.5-7B-Instruct`, `AIRLLM_COMPRESSION`=`4bit`) and fully failure-isolated — a missing/erroring airllm falls back to the raw-corpus training path, so enabling it can never break a normal mango run. The local package is named `airllm_engine` (NOT `airllm`) so it can't shadow the pip package. Validated by `npm run airllm:selfcheck` (hermetic — worker-down degrade + pure clamp/distill threading + route wiring; NO torch/airllm/network); the live high-parameter generate + distill→train path is the runtime check (needs a CUDA torch build to be practical).

## Purely-local guarantees

The project is designed to run end-to-end with **zero outbound network traffic** by default.

- **Server-enforced URL allowlist.** `server/src/config.ts` exposes `localOnly` (env `LOCAL_ONLY`, default `true`). When `true`, `POST /api/connectors` and `POST /api/connectors/select` reject any `baseUrl` whose host is not loopback (`127.0.0.1`, `localhost`, `::1`) or RFC1918 (`10/8`, `172.16/12`, `192.168/16`). The implementation is `isLocalUrl()` in `server/src/util/network.ts` — keep both inputs and outputs going through that helper.
- **Auto-discovery of local runtimes.** On boot and every 60 s, `reconcileDiscovered()` in `server/src/connectors/registry.ts` runs `discoverLocalRuntimes()` (in `server/src/connectors/discovery.ts`) which probes 7 known runtimes in parallel with content-checked probes and a 200 ms timeout per port: Ollama (11434), LM Studio (1234), llama.cpp (8080), Jan (1337), GPT4All (4891), vLLM (8000), TGI (3000). Detected runtimes are upserted as `auto-<kind>` rows; if no row is marked default, Ollama is preferred (native embeddings + streaming).
- **Tauri-side probe.** Browser fetches to non-:8787 ports get blocked by CORS preflight (these servers ship no CORS headers on loopback). The Rust command `probe_local_llms` in `src-tauri/src/llm_probe.rs` mirrors the Node-side probe table and is preferred when `window.__TAURI__` is present. If you change the probe table in either place, port the change to the other.
- **Unified OpenAI-compatible connector.** `server/src/connectors/OpenAICompatibleConnector.ts` drives LM Studio, llama.cpp, Jan, GPT4All, vLLM, and TGI (local) plus NVIDIA NIM and Gemini's OpenAI endpoint (remote) through the OpenAI `/v1/*` endpoints. `embed()` is only attached when the descriptor sets `embeddingModel` — the pipeline's `getEmbedder()` helper relies on `instance.embed` presence rather than a no-op check.
- **Multi-key rotation / failover (free-tier quota multiplier).** The connector resolves a host-scoped key **pool** (`resolveApiKeys`): a comma-separated plural var (`NVIDIA_API_KEYS`, `GEMINI_API_KEYS`/`GOOGLE_AI_API_KEYS`, `OPENAI_API_KEYS`/`LMSTUDIO_API_KEYS`) **plus** the legacy singular var, order-preserving-deduped. With ≥1 keys every request **round-robins** across the pool to spread load (≈Nx the per-key rate limit), and a `429`/`401`/`403` triggers transparent **failover** to the next key — the throttled/exhausted one enters a **cooldown** (short for 429 honoring `Retry-After`, long for auth) so later requests skip it; an exhausted-pool sweep tries cooled keys rather than failing outright. A non-key error (`4xx≠auth`, `5xx`) is surfaced immediately and does **not** burn the pool. A fully-throttled pool throws `ConnectorError(429)` (loud, never a silent empty answer). Failover is on the *initial* response status so streaming + embeddings rotate too. Keys are read from `process.env` only — never persisted to the DB. Validated by `npm run keyrotation:selfcheck` (hermetic — injected fetch, NO network).
- **Embeddings fallback chain.** `getEmbedder()` in `server/src/reasoning/pipeline.ts`: active connector → any local Ollama with `state: "ok"` → null (memory step degrades gracefully with `detail` ending in `"skipped"`). Pipelines on a chat-only runtime (e.g. GPT4All) still complete, just without retrieval-augmented citations.
- **`LocalityBadge` in the UI.** The status panel shows green "Purely local" when every enabled connector has `isLocal === true`, amber "Remote model in use" otherwise (the `/api/health` response carries `locality: "local" | "remote"`).
- **Strict Tauri CSP.** `src-tauri/tauri.conf.json` sets `default-src 'self'` with a `connect-src` that lists exactly the 7 runtime loopback URLs plus the local Node server. Anything else is blocked at the renderer.
- **Web search / research obey the same gate.** The hybrid layer (`web/search.ts`, `web/research.ts`, the `web-search`/`research-web` actions, `POST /api/web/*`, and the pipeline's auto-augmentation) routes every request URL through `isLocalUrl()` under `LOCAL_ONLY`. Under the default `LOCAL_ONLY=true` a *local SearXNG* is reachable (your box reaches the internet; ours never does) but every remote search backend and every internet page fetch is blocked — so "zero outbound by default" holds for search exactly as it does for connectors. **Unlike LLM connectors there is no remote-host allowlist bypass for search**: remote search/research requires `LOCAL_ONLY=false`.

To go **local + internet side by side**: set `LOCAL_ONLY=false` (the single, documented opt-out — the `LocalityBadge` flips amber). Then the brain uses local memory and the live web together: configure a search backend via `WEB_SEARCH_PROVIDER` (`auto`|`searxng`|`brave`|`tavily`|`exa`|`duckduckgo`) with `SEARXNG_URL` or a `BRAVE_API_KEY`/`TAVILY_API_KEY`/`EXA_API_KEY` (auto falls back to keyless DuckDuckGo), and tune when `/api/ask` reaches out with `WEB_SEARCH_MODE` (`smart` default | `always` | `ondemand` | `off`) and the master `HYBRID_RESEARCH` switch. To allow a remote LLM as well, configure an OpenAI-compatible connector with the remote `baseUrl`. The two curated free-tier providers (NVIDIA NIM, Gemini) are reachable even under `LOCAL_ONLY=true` (their exact hosts are allowlisted), so a cloud chat brain does **not** require opening general web egress — just set the key(s) and the connector is auto-seeded (disabled + non-default; you opt in via the picker). Hold several free keys to survive rate limits by setting the plural `*_API_KEYS` var (see "Multi-key rotation / failover" above). The default stays fully local; the guarantee is preserved until you flip the one flag.

## Conventions

- TypeScript `strict: true` is on in both `src/` and `server/`. The frontend build (`npm run build`) and the server `npm run typecheck` both fail on implicit `any` or unchecked nullables.
- React 18 with the automatic JSX runtime (`jsx: "react-jsx"`) — no `import React` needed.
- Three.js is imported as `import * as THREE from "three"`. Examples (`OrbitControls`, `EffectComposer`, `RenderPass`, `UnrealBloomPass`, `GLTFLoader`) come from `three/examples/jsm/...`. Stay on the pinned version (`^0.171.0`) — examples sometimes break across minor releases.
- The server is ESM (`"type": "module"` in `server/package.json`). Relative imports inside `server/src/` must use the `.js` extension even when the source is `.ts` (Node ESM resolver requirement); imports of `shared/` use `.js` too, e.g. `from "../../../shared/pipeline.js"`.
- Shared types live in `shared/` and have **zero runtime dependencies** — they are pure type declarations + plain constants. Keep it that way so both the Vite client and the Node server can import them without a build step.
- `data/` (SQLite DB), `artifacts/` (screenshots), `dist/`, `worker/.venv/`, and `server/dist/` are all gitignored — assume they may not exist on a fresh checkout.
